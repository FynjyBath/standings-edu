# Standings EDU

Простой сервис для ведения таблиц результатов по олимпиадным задачам.

Проект решает две задачи:
- собирает данные об учениках и их решениях из разных источников;
- показывает готовые standings в веб-интерфейсе и через API.

## Что умеет проект

- Генерирует standings в статические JSON-файлы (`generated/`);
- Поддерживает два типа контестов:
  - `tasks`: собирает решения по списку задач;
  - `provider`: берёт готовые standings у внешнего провайдера;
- Поднимает HTTP-сервер для просмотра таблиц;
- Принимает анкеты учеников (intake) через JSON-RPC;
- Вливает анкеты в основную базу учеников отдельной командой merge.

## Для обычных пользователей

### Как устроена работа проекта

Рабочий цикл выглядит так:
1. Вы храните исходные данные в `data/` (ученики, контесты, группы).
2. Запускаете генерацию (`cmd/generate`) и получаете готовые standings в `generated/`.
3. Запускаете сервер (`cmd/server`) и открываете страницы standings в браузере.
4. Новые анкеты приходят в `student_intake.json`.
5. Когда нужно, вливаете анкеты в основную базу `students.json` командой merge.

Сервер кэширует распарсенные standings в памяти и обновляет кэш по времени
изменения файла (`mtime`+размер): после перегенерации новые таблицы
подхватываются автоматически, без перезапуска сервера. Правки одних и тех же
data-файлов через админку выполняются строго по одной (без потери записи при
одновременных действиях).

### Основные данные

Минимально важные файлы:
- `data/students.json` — ученики и их аккаунты;
- `data/contests.json` — список контестов;
- `data/groups/<group_slug>/group.json` — информация о группе (включая `form_link`);
- `data/groups/<group_slug>/contests.json` — контесты группы.

### Контесты группы: ссылка по id или inline-определение

В `data/groups/<group_slug>/contests.json` каждый элемент может быть либо:

- **ссылкой** на контест из глобального `data/contests.json` (как раньше):

  ```json
  { "id": "contest_basics_tasks", "update": true }
  ```

- либо **полным определением контеста прямо в файле группы** — тогда его не
  нужно держать в глобальном `data/contests.json` (удобно для разовых контестов):

  ```json
  {
    "id": "oneoff_2024_10_01",
    "update": true,
    "title": "Разовый контест",
    "score_system": "ioi",
    "source_type": "provider",
    "provider": "codeforces_contest",
    "provider_config": { "contest_id": 1711, "show_unofficial": true },
    "table_name": "Соревновательные",
    "subcontests": []
  }
  ```

Как это работает:
- элемент считается inline-определением, если содержит хотя бы один из ключей
  `title`, `score_system`, `source_type` (или устаревшее `contest_type`),
  `provider`, `provider_config`, `subcontests`, `materials`; иначе это ссылка по `id`;
- формат полей такой же, как в глобальном `data/contests.json` (включая `materials`);
- `id` обязателен и должен быть уникальным в пределах файла группы;
- если `id` есть и в глобальном `data/contests.json`, и inline в группе —
  для этой группы приоритет у inline-определения;
- поле `table_name` не считается inline-признаком: его можно добавить и к ссылке
  на глобальный контест — тогда для этой группы вкладки берутся из ссылки
  (см. раздел про `table_name` ниже), а содержимое контеста остаётся глобальным.

### Тип контеста (`source_type`) и вкладки сводной таблицы (`table_name`)

- `source_type` — тип контеста: `tasks` (собираем сами по списку задач; значение
  по умолчанию) или `provider` (готовые standings у внешнего провайдера).
  Раньше поле называлось `contest_type` — оно продолжает читаться как алиас, но
  в новых данных используйте `source_type`.
- `table_name` — в какие вкладки сводной таблицы (`/standings/<group>/summary`)
  попадает контест. Можно указать одну строку или список строк; имя строки — это
  и есть название вкладки:

  ```json
  { "id": "probnik_1", "title": "Пробник №1", "table_name": ["Тематические", "Пробники"] }
  ```

  - вкладки на странице summary строятся автоматически из всех встретившихся у
    группы `table_name` (в порядке первого появления), плюс вкладка «Все»;
  - контест с несколькими именами показывается во всех этих вкладках;
  - если `table_name` не задан, контест виден только во вкладке «Все»;
  - `table_name` можно задать и на уровне ссылки в файле группы — тогда для этой
    группы вкладки берутся из ссылки (переопределяют `table_name` из глобального
    определения);
  - задаётся прямо в JSON-редакторе админки — отдельного UI не нужно.

### Оценки группы (`grades` в `group.json`)

Опциональная таблица оценок группы. Если поле `grades` есть и в нём непустой
`columns`, на странице группы появляется кнопка с названием из `grades.title`
(иначе «Оценки»), открывающая публичную таблицу `/standings/<slug>/grades`.

Итог по ученику = **взвешенное среднее** столбцов (каждый 0–10), округление —
`round` знаков (по умолчанию 1). Если у ученика для столбца нет оценки, столбец не
идёт в среднее. Перед колонкой «Итог» показывается «Итог точно» — то же среднее
**без** округления, всегда с двумя знаками после запятой.

Пример:

```json
"grades": {
  "title": "Оценки за модуль",
  "round": 1,
  "columns": [
    {
      "id": "activity", "title": "Активность", "weight": 1,
      "type": "table", "table_name": "Тематические",
      "metric": "plus", "normalize": "max"
    },
    {
      "id": "olymp", "title": "Олимпиада", "weight": 1,
      "type": "table", "table_name": "Соревновательные",
      "metric": "score", "normalize": "total"
    },
    { "id": "kontrolnaya", "title": "Контрольная", "weight": 2, "type": "manual" }
  ]
}
```

Столбцы бывают двух типов:

- **`"type": "table"`** — берётся значение из сводной вкладки `table_name`
  (пусто = все контесты группы): `metric` = `"plus"` (число `+`) или `"score"`
  (баллы). Нормируется к 0–10 по `normalize`:
  - `"max"` — по «идеальному ученику»: сумма лучших результатов **каждого
    контеста по отдельности** (выиграл все контесты = 10). Раньше бралась
    максимальная общая сумма одного ученика — теперь топ по каждому контесту
    может быть разным;
  - `"total"` — по максимуму достижимого: для `plus` = число задач, для `score`
    = 100 × число задач;
  - число (напр. `20`) — по фиксированному значению.

  Опционально у табличного столбца — `"upsolving"` (0–1): коэффициент учёта
  дорешки. Вклад задачи = `a + max(0, b−a)·коэффициент`, где `a` — балл в окне
  контеста, `b` — балл в дорешке. То есть основной результат сохраняется
  полностью, а сверху добавляется доля прироста от дорешивания — дорешивать
  всегда выгодно (для `plus`: решена в контесте = 1, дорешана = коэффициент).
  Без поля — прежнее поведение: дорешка на полную. Работает по данным,
  сгенерированным новой версией (в старых файлах баллы не разделены на
  основные/дорешку).
- **`"type": "manual"`** — ручные оценки (0–10). Хранятся в
  `data/groups/<slug>/grades_manual.json`:

  ```json
  { "kontrolnaya": { "ivanov-ii": 8, "petrova-aa": 10 } }
  ```

  (ключ верхнего уровня = `id` ручного столбца, внутри `student_id → оценка`).

Всё это удобнее настраивать через админку: у группы кнопка **«Оценки»**
(`/standings/admin/group-grades?slug=…`) открывает страницу с двумя частями —
**конструктором столбцов** (добавить/удалить/переупорядочить столбцы, задать
тип, вес, вкладку `table_name` из подсказок, метрику, нормировку, коэффициент
дорешки — сохраняется в `grades` внутри `group.json`) и **сеткой ручных оценок**
(ученики × ручные столбцы). Веса относительные. `id` столбца автоподставляется
из названия латиницей; не меняйте `id` ручного столбца, по которому уже есть
оценки, — иначе они «осиротеют». **Важно:** оценки считаются при генерации,
поэтому изменения (и ручные, и из таблиц) появляются после ближайшего
`generate`. Структуру оценок по-прежнему можно править и через JSON-редактор.

Обратная совместимость: нет `grades` / нет `columns` — страница оценок покажет
только конструктор (пустой); нет `grades_manual.json` или записи — ручная ячейка
пустая; ничего не падает.

Поле `materials` в `data/contests.json` (опционально):
- формат: массив объектов `{ "title": "...", "url": "..." }`;
- если `materials` отсутствует или пустой, всё работает как раньше;
- ссылки из `materials` отображаются на странице группы `GET /standings/<group_slug>` внутри блока контеста.

Пример контеста с `materials`:

```json
{
  "id": "contest_basics_tasks",
  "title": "Базовые задачи",
  "score_system": "edu",
  "materials": [
    {
      "title": "Разбор",
      "url": "https://example.com/review"
    },
    {
      "title": "Видеозапись",
      "url": "https://example.com/video"
    }
  ],
  "subcontests": [
    {
      "title": "Разминка",
      "tasks": [
        "https://codeforces.com/problemset/problem/4/A"
      ]
    }
  ]
}
```

### Ссылка на весь контест Codeforces в списке задач

В `tasks`-контесте элементом `tasks` можно указать не только ссылку на задачу, но
и **ссылку на контест Codeforces целиком** (без `/problem/...`):

- `https://codeforces.com/contest/<id>`
- `https://codeforces.com/gym/<id>`
- `https://codeforces.com/group/<gid>/contest/<id>`

Такая ссылка разворачивается во **все задачи контеста** (A, B, C, …) на своём
месте, а идущие следом задачи сдвигаются по меткам. Результаты берутся **одним**
запросом `contest.standings` на контест (не по каждому ученику отдельно) и
раскладываются по ученикам по их codeforces-аккаунтам. Можно смешивать с обычными
задачами и задачами других сайтов в одном подконтесте:

```json
{
  "id": "abcd",
  "title": "ABCD",
  "score_system": "edu",
  "table_name": "Тематические",
  "subcontests": [
    {
      "title": "Задачи",
      "tasks": [
        "https://codeforces.com/group/yjrVEiooaf/contest/701718",
        "https://informatics.msk.ru/mod/statements/view.php?chapterid=1791#1"
      ]
    }
  ]
}
```

Нюансы:
- ссылки на задачи informatics можно давать и со старого зеркала
  `informatics.mccme.ru` — при сопоставлении с посылками оба домена считаются
  одним сайтом, а видимая ссылка в таблице остаётся такой, какой введена;
- групповые/gym контесты требуют, чтобы владелец API-ключа
  (`data/credentials/codeforces_credentials.json`) имел к ним доступ; отдаётся
  полный список задач;
- у **публичных** контестов Codeforces API запрещает фильтрованный
  `contest.standings`, поэтому используется `contest.status`, и в разворот
  попадают только те задачи, к которым была хотя бы одна посылка учеников группы;
- учитывается виртуальное участие и дорешивание (дорешка помечается в скобках).

### Ссылка на весь сборник informatics в списке задач

Аналогично Codeforces, элементом `tasks` можно указать **ссылку на сборник
informatics целиком** — страницу `mod/statements/view.php?id=<N>` **без**
`chapterid`:

- `https://informatics.msk.ru/mod/statements/view.php?id=2296`

При сборке страница сборника читается, из её оглавления берётся упорядоченный
список задач, и ссылка разворачивается во **все задачи сборника** (A, B, C, …) на
своём месте. В таблицу подставляется ссылка **на саму задачу**
(`…view.php?chapterid=<N>#1`), без сборника. Результаты, в отличие от Codeforces,
отдельным запросом не собираются — они берутся из уже скачанных посылок ученика по
обычному сопоставлению `normalized_url` (сопоставление идёт по `chapterid`,
поэтому «браузерная» форма `…?id=<N>&chapterid=<M>` тоже совпадает с посылками).

Ссылка **с** `chapterid` (`…?id=<N>&chapterid=<M>` или `…?chapterid=<M>`) — это
одна конкретная задача, а не сборник, и разворачиванию не подлежит.

### Наследование параметров: глобальное определение vs запись группы

Поведенческие параметры контеста — `table_name`, окно `start_time`/`end_time`,
`freeze`, `zero_penalty`, `summary_total_only`, `hidden` — можно задавать **и** в глобальном
`data/contests.json` (действует для всех групп-ссылок), **и** в записи
`groups/<slug>/contests.json` (только для этой группы). Правило простое:

- параметр задан в записи группы → используется он (переопределяет глобальный);
- не задан → наследуется из определения контеста.

Так один глобальный контест может идти в разных группах в разное время, с разной
заморозкой и т. п., а общие для всех настройки достаточно задать один раз в
глобальном определении. Эти поля в записи-ссылке **не** превращают её в
inline-определение.

Чтобы локально **выключить** унаследованное значение (не просто «не задавать»):
- заморозка: `"freeze": "none"` (в UI — «выключена»);
- штраф: `"zero_penalty": 0`;
- «только сумма»: `"summary_total_only": false`;
- «скрыт»: `"hidden": false` (показывать).

В админке всё редактируется в двух местах: полный набор — в форме контеста
(«Контесты»), переопределения группы — на странице группы. В строке группы пустое
поле означает «как у контеста», а рядом показано наследуемое значение
(«как у контеста (1h)», «насл.: …»).

### Время начала и окончания у tasks-контеста (`start_time` / `end_time`)

У `tasks`-контеста можно задать окно проведения — тогда для сайтов, которые
отдают время посылки (**Codeforces**, **Informatics**), в зачёт идут только
посылки в окне `[start_time, end_time]`, а решённое **после** окончания попадает в
**дорешку** (показывается в скобках, как у CF-провайдера). Посылки **до** начала
игнорируются.

Окно задаётся в глобальном определении или в записи группы (см. наследование
выше). Пример переопределения на стороне группы:

```json
[
  { "id": "kontrolnaya", "update": true,
    "start_time": "2026-09-01T18:00:00+03:00",
    "end_time": "2026-09-01T20:00:00+03:00" }
]
```

До `start_time` сервер **не отдаёт ссылки на задачи** этого контеста (ни на
страницах, ни в сводной, ни в API `/api/groups/<slug>/standings`) — видны только
метки задач и подсказка со временем старта. Ссылки появляются ровно в момент
начала, без регенерации. В админке окно вводится нативным полем даты-времени
(в локальном времени браузера, на сервер уходит ISO со сдвигом).

### Штраф за нули (`zero_penalty`) и показ дорешки

У ioi-контеста (`score_system: ioi`) можно задать `"zero_penalty": 5` — из
суммы вычитается 5 баллов за **каждую** задачу без баллов (пустую или с нулём;
решённая только в дорешке задача от штрафа освобождает). В таблице появляется
колонка «Штраф» и заметка под заголовком; сумма может уйти в минус. Для
плюсовых контестов поле игнорируется. Задаётся в форме контеста («Штраф за
ноль») или в записи группы (переопределение, `0` — выключить) — см. наследование.

Баллы в ячейках ioi-контестов показываются раздельно: `50 (70)` — 50 в
основное время, 70 в дорешке (в сумму идёт максимум); только дорешка — `(70)`.
Если у контеста задано окно, оно подписывается под заголовком таблицы:
«🕒 Контест: 04.07.2026 18:00–20:00 MSK».

### Контест «только сумма» в сводной (`summary_total_only`)

Флаг контеста `"summary_total_only": true` (в форме — чекбокс «В сводной —
только сумма», в записи группы — переопределение `true`/`false`, см.
наследование) сворачивает контест в сводной таблице до одной колонки: сумма
баллов (ioi, со штрафом и дорешкой) или число плюсов (edu) — без колонок по
задачам. Опционально `"short_name"` («Краткое название» в форме) — компактный
заголовок такой колонки; полное название показывается в подсказке при
наведении. Пусто — используется обычное название. Итоги Σ сводной считают такие контесты как обычно. Страница группы
(списком) не меняется — там детализация остаётся. Это отображаемая настройка:
подхватывается при генерации даже у `update=false` контестов, без пересчёта
результатов.

### Скрытие контеста на страницах школьников (`hidden`)

Флаг контеста `"hidden": true` (в форме — чекбокс «Скрыть на страницах
школьников», в записи группы — селект «Показывать» с переопределением, см.
наследование) убирает контест со страниц для учеников: и из списка контестов, и
из сводной. При этом контест **по-прежнему считается** (в том числе учитывается в
оценках — они собираются при генерации по всем контестам) и **виден жюри по
токену** (`?token=…`, как и размороженный просмотр). Это отображаемая настройка:
сервер вырезает скрытые контесты из публичного ответа на каждый запрос, поэтому
смена флага (и токена) действует сразу, без перегенерации.

### Заморозка результатов (`freeze`)

Рядом с окном в записи группы можно задать заморозку — в публичную таблицу
войдут только посылки **до момента заморозки**, всё позже (включая дорешку)
скрыто до разморозки:

```json
[
  { "id": "olympiada", "update": true,
    "start_time": "2026-09-01T18:00:00+03:00",
    "end_time": "2026-09-01T22:00:00+03:00",
    "freeze": "1h" }
]
```

- `"freeze": "1h"` / `"30m"` / `"1h30m"` — момент заморозки = `end_time − freeze`;
- `"freeze": "all"` — заморожено с самого начала;
- `"freeze": "none"` — в записи группы выключает заморозку, заданную в глобальном
  определении контеста;
- требуется заданное окно (`start_time` + `end_time`); длительность больше окна
  приравнивается к `all`.

Заморозку тоже можно задать в глобальном определении (действует для всех
групп-ссылок) или переопределить в записи группы — см. наследование выше.

Таблица генерируется как обычно (кэш посылок продолжает пополняться), но на
странице, в сводной и в API — только «замороженная» часть, с бейджем
«❄ Заморожено» и временем заморозки. **Разморозка**: очистить поле «Заморозка»
в админке (или удалить `"freeze"` из записи) и перегенерировать — появятся
полные результаты с дорешкой. Ограничение то же, что у окна: работает для
сайтов с временем посылок (Codeforces, Informatics); задачи ACMP не фильтруются.
У контестов с `update=false` заморозка меняется только при пересборке таблицы.

### Токен жюри (`group_secret_token`)

Полные версии замороженных таблиц генерируются параллельно (`rows_full`,
`grades_full` в generated-файле) и доступны по секретному токену группы:
`https://…/standings/<slug>?token=<токен>` — страница, сводная, оценки и API
показывают размороженные данные с пометкой «Просмотр без заморозки»; токен
протаскивается в ссылки между страницами. Без токена полные варианты
вырезаются из всех ответов сервера, включая JSON внутри сводной страницы.

Токен хранится в `group.json` (`"group_secret_token"`), управляется со страницы
группы в админке («Сгенерировать» / «Убрать» + готовая ссылка для жюри).
Проверка идёт при отдаче, поэтому смена или удаление токена действует
мгновенно, без перегенерации — если ссылка утекла ученикам, просто
перегенерируйте токен. Публичная разморозка остаётся прежней: убрать `freeze`
и перегенерировать.

По тому же токену доступна **статистика участников группы**: на странице группы
(с токеном) есть ссылка «Статистика участников» → таблица членов с ключевыми
метриками (решено, посылок, активность), из неё — профиль каждого участника
(`/standings/<slug>/student?id=…&token=…`). Профиль по токену показывает только
эту группу в «Позициях» (без утечки других групп) и доступен строго для членов
группы; неверный токен — 404. Это тот же аналитический профиль, что и в админке.

Детали:
- время — ISO 8601 с явным сдвигом (напр. `+03:00`); нужны **оба** поля, иначе окно
  не применяется (при переопределении из группы — оба в записи группы либо
  недостающее наследуется из определения контеста); скрытие ссылок работает и при
  одном `start_time`;
- для IOI (`score_system: ioi`) показывается больший балл — окна или дорешки; если
  победил балл дорешки, ячейка помечается дорешкой;
- сайты **без** времени посылок (**ACMP**) не фильтруются — считаются как обычно
  (всё время), дорешка к ним не применяется;
- окно распространяется на все задачи контеста; к развёрнутым CF-контестам
  (ссылка на контест) окно не применяется — у них своё время;
- влияет только на генерацию; старые сгенерированные файлы не трогаются.

Полезные примеры лежат в `data_example/`.
Этот каталог используется только как шаблон: команды проекта читают данные из `data/`.

Важно:
- `data/students.json` и `data/contests.json` должны существовать (их может создать `cmd/server` при старте);
- группы нужно создать отдельно (можно по примеру из `data_example/groups/group_example/`).

Быстрый старт из примеров:

```bash
mkdir -p data/groups/group_example
cp data_example/students_example.json data/students.json
cp data_example/contests_example.json data/contests.json
cp data_example/groups/group_example/group_example.json data/groups/group_example/group.json
cp data_example/groups/group_example/contests_example.json data/groups/group_example/contests.json
cp data_example/student_intake_example.json data/student_intake.json
```

После этого можно сразу запускать генерацию и сервер.

### Как сгенерировать standings

Базовый запуск:

```bash
go run ./cmd/generate
```

Частые полезные флаги:

```bash
go run ./cmd/generate \
  -data-dir ./data \
  -generated-dir ./generated \
  -group group_example \
```

Что произойдёт:
- в `generated/groups.json` появится список групп;
- в `generated/standings/<group>.json` появятся таблицы по группам.

### Credentials для источников

- `informatics`:
  - используется `-informatics-creds-file` (по умолчанию `./data/credentials/informatics_credentials.json`);
  - файл должен содержать `username` и `password`;
  - если файла нет, источник `informatics` просто отключается (с предупреждением в лог),
    `cmd/generate` не падает — задачи informatics в этом случае не будут засчитаны;
  - если файл есть, но невалидный (битый JSON/нет логина), `cmd/generate` завершится с ошибкой.
- `codeforces`:
  - используется `-codeforces-creds-file` (по умолчанию `./data/credentials/codeforces_credentials.json`);
  - файл опциональный;
  - если файл отсутствует или в нём пустые `key`/`secret`, клиент работает в anonymous mode;
  - если файл существует, но JSON невалидный, `cmd/generate` завершится с ошибкой.

Формат `codeforces_credentials.json`:

```json
{
  "key": "YOUR_CODEFORCES_API_KEY",
  "secret": "YOUR_CODEFORCES_API_SECRET",
  "base_url": "https://codeforces.com/api"
}
```

`base_url` опционален: если не задан, используется `https://codeforces.com/api`.

### Как запустить сервер

Базовый запуск:

```bash
go run ./cmd/server
```

После `clean clone` эту команду можно запускать сразу, без ручного `mkdir`/`touch` для runtime-файлов.

При старте сервер делает bootstrap runtime-структуры:
- создаёт `generated/`, если каталога нет;
- создаёт `generated/standings/`, если каталога нет;
- создаёт `data/`, `data/groups/` и `data/credentials/`, если их нет;
- создаёт `data/students.json` и `data/contests.json` со значением `[]`, если файлов нет;
- создаёт `data/student_intake.json` со значением `[]`, если файла нет.
- создаёт `data/student_intake_admin.json` со значением `[]`, если файла нет.

Важно:
- существующие файлы не перезаписываются;
- если по ожидаемому пути лежит объект другого типа (например, файл вместо директории), сервер завершится с понятной ошибкой;
- `web/templates` и `web/static` не генерируются: сервер только проверяет, что это существующие директории.

После запуска откройте:
- `http://localhost:8080/standings` — список/входная страница;
- `http://localhost:8080/standings/<group_slug>` — таблицы группы;
- `http://localhost:8080/standings/<group_slug>/summary` — сводная таблица;
  вкладки внутри страницы строятся из поля `table_name` контестов (см. ниже),
  плюс вкладка «Все».

(Старые адреса `/summary-edu` и `/summary-olymp` продолжают работать и открывают
ту же сводную страницу — на случай сохранённых ссылок.)

API:
- `GET /healthz`
- `GET /api/groups`
- `GET /api/groups/{group_name}/standings`
- `POST /api/rpc`

### Админка

Админка доступна по `GET /standings/admin` и закрыта Basic Auth (логин/пароль из `data/credentials/admin_credentials.json`).

Что есть в админке:
- действия `generate` (сборка всех таблиц) и `create_group`;
- **форма «Ученики»** (`/standings/admin/students`) — добавление/редактирование/удаление
  учеников и их аккаунтов (при удалении ученик убирается и из групп); у каждого
  ученика кнопка **«Профиль»**;
- **профиль участника** (`/standings/admin/student?id=…`) — админский аналитический
  вид: сводка (решено, посылок, активность за 7/30 дней, активных дней, последняя
  активность), метрики скорости (среднее число посылок до решения, решено с первой
  попытки), счётчики по сайтам, позиции в группах (место по доске почёта и по
  оценкам), график активности за 90 дней и лента последних посылок. Лента и
  скорость строятся по посылкам со временем — **Codeforces и Informatics**; ACMP
  времени не отдаёт (по нему только «решено/попытки»). Профили пишутся при
  генерации в `generated/students/<id>.json`, обновляются после каждого `generate`;
- **форма «Контесты»** (`/standings/admin/contests`) — конструктор task- и
  provider-контестов (метаданные, `table_name`, подконтесты с задачами по строкам,
  `provider_config`); окно `start/end` здесь не редактируется — оно задаётся на
  стороне группы;
- **страница группы** (`/standings/admin/group?slug=…`) — удаление участников
  (добавляют формы Яндекса) и управление контестами группы: список её контестов
  (ссылки и inline) с флагом `update`, переопределением `table_name` и окном
  `start/end` у ссылок, кнопка «Добавить ссылку» (выбор из глобального
  `data/contests.json`, новый контест встаёт сверху) и «+ inline-контест» (та же
  форма контеста, но определение хранится в группе);
- по кнопкам у группы: «Аккаунты» (списки по сайтам) и «Оценки» (сетка ручных оценок);
- **JSON-редактор** для `data/students.json`, `data/contests.json` и group-файлов —
  остаётся как «люк»: формы редактируют те же файлы, всё взаимозаменяемо;
- отдельная кнопка для открытия `data/student_intake_admin.json` в merge-сценарии intake;
- блок результата последнего admin-действия с кодом выхода и полным stdout/stderr.

Формы читают и пишут те же JSON-файлы (с сохранением всех полей), так что их можно
свободно чередовать с ручным редактированием. После изменений не забудьте «Сгенерировать».

Отдельный flow для intake merge через staging:
1. Нажмите кнопку `Редактировать intake staging для merge`.
2. Если `data/student_intake_admin.json` пустой или отсутствует, админка переносит в него текущее содержимое `data/student_intake.json` и очищает `data/student_intake.json`.
3. В редактор открывается `data/student_intake_admin.json`.
4. Нажмите `Пробный запуск (что куда)` — dry-run: покажет таблицу «какая анкета
   в какого ученика разрешится (новый/обновление) и в какие группы попадёт (уже
   состоит / добавится)», ничего не записывая. Удобно проверить перед merge.
5. После правок нажмите `Сохранить и сделать merge intake`.
6. Админка сохраняет staging-файл и запускает:
   - `./bin/merge_students -data-dir <dataDir> -intake-file <dataDir>/student_intake_admin.json -write`
7. Логи merge показываются в блоке `Результат последнего действия`.

Важно:
- новые анкеты из `POST /api/rpc` продолжают записываться в обычный `data/student_intake.json`;
- staging-flow работает с отдельным `data/student_intake_admin.json` и не перетирает новые submit’ы.

### Как отправлять анкеты (intake)

Сервер принимает JSON-RPC метод `student_intake.submit` через `POST /api/rpc`.

Минимальный пример:

```json
{
  "jsonrpc": "2.0",
  "id": 1,
  "method": "student_intake.submit",
  "params": {
    "full_name": "Иванов Иван Иванович",
    "codeforces": "tourist",
    "informatics": "12345",
    "group": "group_example"
  }
}
```

Что важно:
- `full_name` обязателен;
- остальные строковые поля считаются аккаунтами (`site=имя поля`, `account_id=значение`);
- поле `group` (если передано) только запоминается в анкете и применяется позже, при merge;
- анкета сохраняется **только** в `data/student_intake.json` (по умолчанию);
  заполнение анкеты не трогает `data/students.json` и файлы групп — ученик попадает
  в основную базу и в нужную группу лишь на этапе подтверждения (merge);
- форму можно заполнять несколько раз: записи сопоставляются по ФИО, при повторном
  заполнении обновляются только переданные поля (аккаунты для того же сайта
  перезаписываются, новые — добавляются), новая запись создаётся только при первом
  заполнении. Та же логика merge применяется и при сливании intake в основную базу.

### Защита приёма анкет токеном

По умолчанию `POST /api/rpc` открыт: анкету может прислать любой, кто достучится
до сервера (страницы standings публичны и крутятся на том же сервере). Чтобы
принимать анкеты только из своей интеграции Яндекс.Формы, включите секретный токен.

- **Как называется и где лежит:** файл `data/credentials/intake_credentials.json`
  формата `{ "token": "ДЛИННЫЙ_СЛУЧАЙНЫЙ_СЕКРЕТ" }` (путь переопределяется флагом
  `-intake-creds-file`). Файл лежит в `data/credentials/`, в репозиторий **не**
  коммитится (каталог `data/` в `.gitignore`). Шаблон —
  `data_example/credentials/intake_credentials_example.json`.
- **Как добавить:**
  1. сгенерируйте секрет, например `openssl rand -hex 32`;
  2. создайте `data/credentials/intake_credentials.json` с этим значением в поле `token`;
  3. перезапустите сервер (в логе появится `intake token configured; POST /api/rpc требует токен`).
- **Как присылать токен из Яндекс.Формы:** в настройках интеграции (серверная
  отправка на ваш URL) добавьте токен одним из двух способов:
  - заголовок `X-Intake-Token: <токен>`; **или**
  - константное поле `token` в теле запроса (`params.token`), не привязанное к
    вопросу формы — тогда ученики его не видят.

  Токен — это серверная настройка интеграции, в саму форму/страницу он не попадает,
  поэтому ученикам недоступен.
- **Поведение:** если токен задан, запросы без правильного токена получают `401`;
  поле `token` не сохраняется как аккаунт. Если файла нет (или он пустой) — защита
  выключена, сервер при старте пишет предупреждение. Если файл есть, но без `token`
  или с битым JSON — сервер не стартует (ошибка конфигурации).

### Как влить анкеты в `students.json`

Проверка без записи:

```bash
go run ./cmd/merge_students -dry-run
```

Реальная запись:

```bash
go run ./cmd/merge_students -write
```

По умолчанию команда использует:
- `data/students.json`
- `data/student_intake.json`

После `-write`:
- `students.json` обновляется;
- каждый ученик из анкеты с указанной группой добавляется в
  `data/groups/<slug>/group.json` (`student_ids`); если группы ещё нет, она
  создаётся автоматически (директория + `group.json` + пустой `contests.json`);
- `student_intake.json` очищается (`[]`).

### Типичный сценарий использования

1. Подготовить `data/students.json`, `data/contests.json` и файлы групп.
2. Запустить `go run ./cmd/generate`.
3. Запустить `go run ./cmd/server`.
4. Открыть `/standings/<group_slug>` и проверить результат.
5. Принимать новые анкеты через `POST /api/rpc`.
6. Периодически запускать `go run ./cmd/merge_students -write`.
7. Снова запускать генерацию, чтобы standings учитывали обновлённых учеников.

## Для разработчиков

### Как устроен проект

На высоком уровне:
- `cmd/generate` — офлайн pipeline генерации;
- `cmd/server` — веб и API над уже сгенерированными файлами;
- `cmd/create_group` — создание пустой группы (директория + `group.json` + `contests.json`);
- `cmd/merge_students` — merge intake в основную базу учеников.

### Основные директории и ответственность

- `cmd/` — точки входа CLI;
- `internal/domain/` — доменные модели и общие правила нормализации;
- `internal/storage/` — чтение исходников из `data/` и запись `generated/`;
- `internal/source/` — внешние интеграции:
  - task-сайты (`SiteClient`),
  - standings-провайдеры (`ContestProvider`),
  - единый `Registry`;
- `internal/standings/` — основной pipeline построения standings;
- `internal/studentintake/` — intake + merge + синхронизация группы;
- `internal/httpapi/`, `internal/web/` — HTTP-слой и шаблоны.

### Поток данных

1. `storage.SourceLoader` читает исходные JSON из `data/`.
2. `standings.Builder`:
   - выбирает нужные группы/контесты;
   - для task-контестов собирает результаты через `source.SiteClient`;
   - для provider-контестов вызывает `source.ContestProvider`.
3. `standings.Pipeline` объединяет обновлённые и неизменяемые контесты группы.
4. `storage.GeneratedWriter` пишет итог в `generated/`.
5. `httpapi` читает `generated/` и отдаёт UI/API.

### Как добавить новый сайт (task-based)

1. Создайте реализацию `SiteClient` в `internal/source/<site>.go`.
2. Реализуйте методы:
   - `FetchUserResults(ctx, accountID) ([]TaskResult, error)`
   - `MatchTaskURL(taskURL string) bool`
   - `SupportsTaskScores() bool`
3. Зарегистрируйте клиент в `cmd/generate/main.go`:
   - `registry.RegisterSite("<site>", client)`
4. Добавьте аккаунты этого сайта в `data/students.json`.

Почему это важно:
- `MatchTaskURL` влияет на определение источника для задач;
- если URL задач определяются неверно, решения не попадут в standings.

### Как добавить нового standings provider

1. Создайте реализацию `ContestProvider` в `internal/source/<provider>.go`.
2. Реализуйте:
   - `ProviderID() string`
   - `BuildStandings(ctx, input) (domain.GeneratedContestStandings, error)`
3. Зарегистрируйте в `cmd/generate/main.go`:
   - `registry.RegisterProvider(provider)`
4. Добавьте контест в `data/contests.json`:
   - `source_type: "provider"`
   - `provider: "<provider_id>"`
   - `provider_config: {...}`
   - при необходимости `materials: [{ "title": "...", "url": "..." }]`
5. Подключите контест к группе через `data/groups/<group>/contests.json`.

### Провайдер `codeforces_contest`

- `provider_config`: `{ "contest_id": <int>, "show_unofficial": <bool, по умолчанию true> }`.
- Для обычных (не-gym) контестов Codeforces API больше не отдаёт
  отфильтрованный `contest.standings` обычным пользователям
  (только полный анонимный `contest.standings?contestId=<id>`), поэтому таблица
  строится из `contest.status` по handle участников группы; места считаются
  среди участников группы. `show_unofficial: true` учитывает виртуальное участие
  и дорешивание.
- Для gym-контестов (`contest_id >= 100000`) используется `contest.standings`
  с fallback на `contest.status`.
- Дорешивание (посылки после контеста, `participantType=PRACTICE`) показывается
  теми же знаками/баллами, но **в круглых скобках** (`(+)`, `(42)`) и приглушённым
  стилем; на место и штраф дорешка не влияет (место/штраф считаются только по
  результатам во время контеста), но в суммах «Решено»/«Баллы» учитывается.

### Места в таблицах

- Контест по внешней таблице (`html_table_import`) — места берутся **из самой
  таблицы** как есть.
- Таблицы, которые сервис строит сам (контесты по набору задач и
  `codeforces_contest`), — места проставляются **самим сервисом**, относительно
  участников группы (1..k, равные результаты дают диапазон вида `3-5`).

### На что смотреть при расширении

- Нормализация URL задач:
  - используйте единый `domain.NormalizeTaskURL`;
  - в `data/contests.json` URL должны совпадать по смыслу с тем, что возвращают клиенты;
  - ссылки Codeforces на задачу (`/contest/<id>/problem/<idx>`,
    `/problemset/problem/<id>/<idx>`, `/gym/<id>/problem/<idx>`) приводятся к
    единому виду, поэтому любую из этих форм можно указывать в `data/contests.json`.
- Нормализация сайтов и аккаунтов:
  - site хранится в нижнем регистре;
  - пустые `account_id` не должны попадать в данные.
- Совместимость выходного формата:
  - `BuildStandings` провайдера должен заполнять `domain.GeneratedContestStandings` без нарушения текущих полей UI/API.

## FAQ / примечания

**Почему на странице нет таблиц?**
- Обычно не запускалась генерация или для группы нет обновляемых контестов.

**Нужны ли креды Informatics всегда?**
- Нет, только если вы используете `informatics` как источник задач.

**Нужны ли креды Codeforces всегда?**
- Нет. Публичные методы работают анонимно, а API-ключ/секрет нужны только для signed requests.

**Можно ли запускать только одну группу?**
- Да: `go run ./cmd/generate -group <group_slug>`.

**Где смотреть примеры входных данных?**
- Все примеры лежат в `data_example/` и не используются автоматически.

**Нужно ли вручную создавать `generated/` и `student_intake.json` перед `cmd/server`?**
- Нет. Сервер сам создаёт недостающие runtime-пути при старте.
